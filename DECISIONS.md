# Decisions for this fork

- [D-20261027-1] The fork's TVs update only from LanceSandino/cleanyourtv-WebOS (updater, themes, compatibility list, installer, Homebrew Channel listing); upstream changes arrive only through a reviewed merge into the fork — a root service must not pull unreviewed code from another owner's repository (status: active)
- [D-20261027-2] Fork releases are built locally from reviewed source with `python3 ipk/build.py` (CYTV_REPO=LanceSandino/cleanyourtv-WebOS) after `sh tools/check.sh` passes, and published to the fork with `gh release create`; the fork's tag of a version may point at a different commit than upstream's tag of the same name (status: superseded by D-20261027-7)
- [D-20261027-3] The screensaver never syncs the family library to the TV: it reads the photo ids and fetches one photo at a time (plus the next) into a bounded cache (30 photos / 40 MB), purging what the server hides — the owner asked not to pull all photos to the TV, and family-calendar requires hidden photos to disappear on every display (status: active)
- [D-20261027-4] The TV reaches the family-calendar server only through its read-only photo feed with a photos:read bearer token and the server's root certificate pinned from the setup code; the token never leaves the service (not to the launcher, not in status replies) — the household server's display cookie can write data and must not sit on a rooted TV (status: active)
- [D-20261027-5] The screensaver's source is a generic "Photo feed" (two read-only calls and a cyfp1 setup code, documented in docs/screensaver.md), not a family-calendar or Frameo integration — the owner wants other people to be able to use it with their own servers; D-20261027-3 and D-20261027-4 apply to any feed (status: active)
- [D-20261027-6] Pages prove they are ours with the per-install API token (apitoken.js), which is enforced only after every app received it and one sent it back, and dropped again when an app could not get it — a token that bricks Home on an untested TV is worse than the weakness it closes (status: active)
- [D-20261027-7] Fork releases are made by running the Release workflow by hand on reviewed `dev` (it checks, raises the version, moves `main`, builds with CYTV_REPO set to the fork and publishes); never on a schedule — the owner asked for the workflows to work as designed, and a clean CI build from the repository is easier to trust than a local one. v1.6.9 stays the one release built locally (status: active)
- [D-20261027-8] Continue watching is built per source the TV can read without LG's cloud or ads (Telemachus on the TV, LG's local recents list; Plex and Stremio next through their own sign-in links, not by reading other apps' stored logins); LG's per-show rows come from its servers (sdx) and are not used — the owner asked for the same without ads, and reading other apps' credential storage was refused by the permission system and is brittle (status: active)
- [D-20261027-9] Continue watching shows only things started and not finished (one card per show, labelled with its source, removable with hold OK), never app shortcuts; LG's recents list is no longer read. Supersedes the "LG's local recents list" part of D-20261027-8 — on the owner's TV the recents cards repeated tiles already on Home and Telemachus's channel lineup looked like unexplained episodes (status: active)
- [D-20261027-10] Continue watching cards are shown only under the highlighted app they belong to (a row opened under that app's row after 400 ms; Plex's under Plex and PLX), not as a standing row on Home, and an app may show several (Telemachus: what is in progress, then up to four of its channel's next). Supersedes the "one card per show" part of D-20261027-9 — the owner asked for episodes only when their app is selected, with several to choose from (status: active)
- [D-20261027-11] The other apps' rows come from LG's content miner on the TV (its db8 kind com.webos.service.contentminer.contents:1, read with luna-send -a as that service, read only), opened with LG's contentTarget deep link; LG's ad manager is never called and promoted items are dropped. Supersedes the part of D-20261027-8 that kept LG's per-app rows out — the owner allowed acting as LG's own services as long as no ads are shown, and the miner's data is already on the TV (status: active)
- [D-20261027-12] The launcher follows the service: a service running as the release on offer installs that release's launcher (once per pair, written in D/paired, only while Home or the manager is in front), and the manager offers one Update row for both. Rollback stays launcher-only (the previous installed copy, D/app.prev): a service rolled back from backup/service-prev.tgz would be re-applied from the installed package by watchPackage — the owner found the launcher several releases behind after updating the service alone (status: active)
- [D-20261027-20] The Sonos volume on screen is read only by construction: helper/sonos.js can send only GetVolume and GetMute (plus SSDP search, description GET and event (un)subscription), follows changes by UPnP events on an opt-in, guarded LAN port (reading once a second only when events cannot arrive), and stays off by default — the owner's household sleeps with the soundbar muted or low, so nothing may ever be able to raise it (status: active)
- [D-20261027-21] LG's own volume bar is hidden, while the Sonos volume shows and the sound goes to HDMI ARC/eARC or optical, through LG's configd setting com.webos.surfacemanager.volumeOSD written as a one-key file in configd's RAM runtime layer and re-read with reconfigure, not by mounting over LG's files or QML; on webOS 25 only (tvprofile lgVolumeBar), on by default with the Sonos option — the owner wants only our bar for the soundbar, and this is LG's own switch, leaves every LG file as it is and is gone after a restart (status: superseded by D-20261027-22)
- [D-20261027-22] The service's overrides of LG's configd settings live in the RAM layer TV Region Manager Options (/var/run/tvconfig/rmm/<country>, priority 154), written by one helper (lgconfig.js) that records what it wrote in /tmp and only ever replaces or removes those exact files, then reconfigure; LG's app pre-loading is stopped that way (supportAppList with only com.webos.app.home and org.webosbrew.* on, a debloat group on by default) with a restart of preload-manager.service, which reads its list only at start. Supersedes the layer choice of D-20261027-21 — configd selects the remote layer only at boot, before its folder exists, so 1.6.19's file was never read; Lance asked for pre-loading to be blocked with one mechanism for both (status: active)
- [D-20261027-23] LG's app pre-loading is stopped with the preload manager's own setPreloadPolicy ({"application":{"id","isEnabled":false}}, held in its memory until it restarts) for every app it would pre-load except com.webos.app.home and org.webosbrew.*, only for apps already allowed (on webOS 25 the call also marks an app allowed in /var/preferences/webos-preload-manager-conf.json), re-applied every 2 min and after the service starts, nothing restarted. Supersedes the pre-loading part of D-20261027-22 — on the owner's TV the preload manager kept its own state after a restart and ignored configd's supportAppList, while setPreloadPolicy with isEnabled took effect at once; Lance asked for whatever works best (status: active)
- [D-20261027-13] Holiday themes are ordinary data-only themes with a "holiday" date range (MM-DD) and an effects.particles effect; with Holiday themes on (off by default) the service applies the one for today over the chosen theme (its values as the base, so layout, wallpaper and typeface stay; the holiday's own accent), never changes the saved theme, and downloads it up to 3 days before. Effects are a few CSS-animated elements (transform/opacity only) behind the UI — the owner asked for holiday themes; themes must stay data, never CSS or script (status: active)
- [D-20261027-14] Holiday decorations are still pictures (effects.overlay: a transparent frame drawn once behind the UI), never animation: effects.particles is removed. Supersedes the effects part of D-20261027-13 — the owner asked for nothing that moves unless it can be guaranteed not to slow the TV, which cannot be promised on webOS 5's GPU; the frames are our own SVG drawings rendered by tools/holiday-art.mjs (status: active)
- [D-20261028-1] Upstream (lasharor/cleanyourtv-WebOS) changes come in by reviewed cherry-pick with their authors kept and AI co-author trailers removed, never by a blind merge: duplicates of fork features (uninstall) and anything that animates are left out, and security-relevant changes are narrowed to the fork's rules (the webOS 4 origin without the live app) — the fork has diverged in the same files, and its audit decisions stand (status: active)
- [D-20261029-1] For an app LG's content miner has no record of, its row comes from LG's app manager (com.webos.applicationManager/getAllContents, read only, as ourselves): the rows apps write themselves (Netflix, Prime Video), their Continue watching shelf first; the miner's record stays first for every app it has, and the apps' onShow calls are never made. Extends D-20261027-11 (status: active)
- [D-20261029-2] A file that a running LG process has loaded (the input hook libinputhookpp.so in lginput2) is never written over in place by setup, update or rollback: unchanged it is left alone, changed it is written beside it and renamed over it, and the rollback archive leaves it out — cp onto the mapped library truncated it, lginput2 crashed within a second on every update, and LG answered each crash with a full reboot at the next standby (rebootByFault, LG's Home first); Lance reported the slow wakes (status: active)
- [D-20261029-4] Disney+ Continue watching is read from Disney itself (explore partner/continueWatching), with the TV signed in through Disney's own TV-code flow (disneyplus.com/begin) as Disney's web player does it: its public key is read from the sign-in page at run time and never committed, Disney's socket is held only while a code waits, and only the account's refresh and access keys are kept (config.json). Extends D-20261027-8 — LG's Disney+ row is LG's seasonal picks with nothing of the account's, the Disney+ app on the TV is an encrypted bootstrap of Disney's hosted player, and Lance asked for Disney+'s own Continue watching; a sign-in with the password on the TV was ruled out (status: active)
- [D-20261029-3] The fork supports webOS 25 (SDK 10: Node.js 16.20, Chromium 120) and newer only; webOS 5 and 6 (Node.js 8.12, Chromium 68/79) and webOS 22 to 24 are dropped. The service may use what Node 16 has and the pages what Chromium 120 has (ES5 code is not rewritten for its own sake, and the Node 8 helpers stay until cleaned up); the tests run on the current Node with rules for what Node 16 lacks, the page checks run in Chrome for Testing's headless shell 120.0.6099.109, and install.sh and bootstrap.sh refuse an older TV before changing anything (FLOOR in helper/tvprofile.js). Replaces the Node 8.12 / Chromium 68 floor of AGENTS.md rule 3 — the owner's only TV is webOS 25, and the old engines forced Node 8 rules, ES5 pages and flaky Chromium 68/79 checks in CI; upstream cherry-picks (D-20261028-1) stay possible but conflict more as the code diverges, and the fork's releases no longer serve older TVs (status: active)
- [D-20261029-5] Continue watching can be built without anything LG's servers sent: of LG's rows, an app's own row is one whose launch point names a local source for the miner (previewMetadata SOURCE_LOCAL*: Netflix, Prime Video), every other row is LG's pick; with LG's picks off the miner's database is not read. LG's content miner is never blocked by host (homeprv shares <region>.tv.wiselg.com with LG Channels, voice and sign-in) nor before it starts (that needs LG's files changed, and its wake of the Homebrew Channel may be what starts the boot scripts on some TVs): the opt-in debloat group "miner" stops it when the boot scripts start and stubs its program in RAM. Extends D-20261029-1 — the owner asked for our own miner that keeps the apps' data and sends LG nothing (status: active)
- [D-20261029-6] What must stay on while the TV sleeps, or runs all the time, lives on a home server (the hub, hub/server.js: Wake-on-LAN, the kept phone page, later history of the TV's readings), not on the TV; the TV keeps only cheap work done on demand. The hub answers only home-network addresses, forwards only to the TV's own LAN server with the phone's key and Host header unchanged (the TV's checks stay the gate), runs as nobody with no capabilities on a read-only root, and keeps the TV's MAC to itself — Lance asked for the wake helper on Sandino-Ubuntu in /opt and to keep the TV's resources in mind (status: active)
- [D-20261029-7] TV health is read in the service from /proc and /sys only while someone looks (no timer, no program per reading; df at most once a minute where Node 16 has no statfs), one reading per 2 s shared by every viewer, CPU from /proc/stat deltas and never /proc/loadavg; nothing is kept on the TV: history, graphs and alerts belong on an always-on computer that reads the phone endpoint with its own paired key. Off the TV it is reachable only through the phone remote's LAN server with a paired phone's key (a whitelist, read only, nothing secret: no token, key, address or MAC), never on a new port or without a key — Lance asked for glasshouse's metrics but faster and more secure; glasshouse serves everything unauthenticated on :8080 and polls a 120-point history on the TV (status: active)
- [D-20261029-8] Search on Home ("where to watch") uses only what is on the TV or in the user's own accounts, and the service never sends the words anywhere (only the app the user opens gets them, as its launch parameters): first the titles of the rows the service already read for Continue watching (no read of its own, with Home's switches, so LG's picks only while they are on) and the installed apps' own in-app search from their appinfo (inAppSearchParams, the words in the launch parameters); later, only if the first step proves solid, Telemachus's library on the TV, the linked Plex server's own search and Stremio's public Cinemeta catalog (no account). Never LG's search or voice services (sdp_search, its voice proxy), JustWatch or Reelgood, the streaming services' web APIs or Google's; TMDB's watch providers only as a later opt-in. Netflix's and Prime Video's inAppVoiceIntent wait until their intent names are checked on a TV. The owner asked for a cross-app search without LG's tracking, and every search service named above would receive each title typed with the TV's or the user's identity (status: superseded by D-20261029-13)
- [D-20261029-9] Questions LG asks with a deadline (the screensaver request) are answered by the service, never by a web page: a page in the background or reloading answers late, LG's fault manager counts that as a fault ("Request Screen Saver" timed out, client cleanyourtv) and reboots the TV fully at its next standby; seen on the owner's TV on 2026-10-29 (status: active)
- [D-20261029-10] LG's web inspector (WebAppMgr's DevTools, which LG's webapp-mgr.sh always opens on 0.0.0.0:9998 with no authentication) is closed by default with a copy of LG's start script without --remote-debugging-port, written in /tmp and bind-mounted over /etc/systemd/system/scripts/webapp-mgr.sh once per start (scripts/devtools-close.sh, undone by devtools-undo.sh), and WebAppMgr is restarted once, only at boot from 10-cleanyourtv-home, only when the running one has the port, and before sam's restart; the manager's switch (D/devtools-open) only mounts or unmounts and takes effect at the next start, never restarting WebAppMgr while the TV is used. The switch is removed rather than narrowed: --remote-debugging-address is not in WebAppMgr's engine (libcbe.so has only remote-debugging-port and -pipe), and the kernel has no iptables — Lance asked for 9998 closed in RAM at one restart's cost (status: active)
- [D-20261029-11] The boot debloat runs as soon as the boot scripts start, from 10-cleanyourtv-home before it stages Home (15-cleanyourtv-debloat early), and once more when LG's boot is done (/tmp/boot-done, a bounded wait), instead of 60 s after the boot hook; a Home that was not taken over lifts it again. Daemons that LG starts after the boot scripts are held by the existing stub bind mount, not by systemd: a runtime mask lives in /run/systemd/system, which ranks below LG's units in /etc/systemd/system, and needs a daemon-reload during LG's boot. Measured on the owner's 86UR8000: the boot scripts start at 44 s, LG's activity manager launches sportsalarm, livepick-plus, adoverlay-service and acr2 from 58 to 61 s, nudge starts at boot-done (85 s); the old pass stopped them at 113 s (nudge at 204 s) (status: active)
- [D-20261029-12] The debloat stops these as well, on the owner's 86UR8000 reading: rdxd (stopped) and uploadd (stubbed) with the logs, livepick-plus (stubbed) with the tracking, nudge stubbed instead of stopped (it ignores SIGTERM), and a new default-on group lan for LG's network services a TV does not use (cups-lpd.socket on 515/tcp, ninfod). Left running on purpose: dmost (LG Channels and its beacon, which leaves before the boot scripts; lgservers blocks its server), crashd, faultmanager, PmLogDaemon/PmKLogDaemon, sdp-server-notice and Google Cast's log service — Lance asked for LG's tracking and log-upload daemons to be stopped where it is safe (status: active)
- [D-20261029-13] Search on Home also says where any title can be watched (Where to watch), and for that the service sends the words typed, once the typing stops, to the services the owner uses: Plex's catalogue (Plex Discover: search and availabilities in LG's service country, with the linked Plex account's key and this install's Plex client id), Disney+'s own search (when linked, with its key), the linked Plex server's /hubs/search, Stremio's public Cinemeta catalogue (only when Stremio is installed, no key) and Telemachus on the TV; never a device id, never LG's search or voice services, JustWatch, Reelgood, the streaming services' web APIs or Google's; TMDB watch providers only as a later opt-in. Plex's links are affiliate trackers and are never opened or asked: only the service's own link inside them is read, for the id the installed app opens with (deeplinks.js; Disney+ by its entity id, Netflix, Prime Video and Apple TV in the format their own rows on the TV use, the others opened as they are); Plex's sponsored flag and order are ignored, the apps on this TV come first, a subscription or free before rent and buy. A launcher switch, Customize > Search > "Ask services where a title is" (search.where), is on by default and off keeps the local-only search of D-20261029-8. Supersedes D-20261029-8 — Lance asked for it: "if I look up bluey it should show where that would be", and searching only titles already known is "dumb" (status: active)
